# Decisions

Why each lock in [`.agents/rules.md`](.agents/rules.md) exists. The rules say *what*; this file says *why*, so a future maintainer can tell a load-bearing constraint from a habit and change the former deliberately. One paragraph per decision. When a lock changes, update its paragraph in the same PR and record what replaced it. Items marked **deferred** are agreed designs waiting on a release boundary; the detail is in the protocol 1.1 proposal referenced below.

Item IDs (`D5`, `A8`, `Q4`, …) are from the 2026 maintainer review, its remediation plan, and the protocol 1.1 design spike. Those are maintainer notes, not files in this repository; the IDs are kept so the entries can be matched to them.

## Package shape

### Published contract types do not import optional peer `typebox`

`@ts-pf/contract` is what every typed client imports. `typebox` is an optional peer because only TypeBox schemas need it at runtime, and the adapter loads `typebox/value` with a dynamic import when one shows up. A type-only `import { Static, TSchema } from 'typebox'` in `schema.ts` was emitted into `dist/schema.d.ts`. TypeScript resolves that import when it loads the declaration, so a consumer type-checking dependencies (`skipLibCheck: false`) got `TS2307: Cannot find module 'typebox'` unless they installed the peer. `skipLibCheck: true` hides the error, which is why it lasted; `@chief-ai/app-kit-ts-pf` carried `typebox` as a devDependency so its pack check (skipLibCheck off) could resolve the import. Inference now walks `~kind` in `typebox-static.ts`, the same structural idea as the Zod `_zod` branch, which does not import `zod`. A parity test compares that walk to `Static<>` for the shapes this library uses. `check:exports` fails if a packed `@ts-pf/contract` or `@ts-pf/docs` `.d.ts` imports `typebox` (docs has the same optional peer, and a type import there would be the same `TS2307`). Do not put the import back to fix an unmatched shape; extend the walk and the parity test. `skipLibCheck: true` is not a substitute: the optional peer has to be optional for types too.

### `contract` and `protocol` are siblings; `ProtocolErrorCode` is duplicated

`@ts-pf/contract` is what a split-repo client imports to get types, and what `@ts-pf/codegen` emits against. It must stay free of anything that is not "the shape of procedures": no wire, no HTTP, no runtime error class. `@ts-pf/protocol` is the wire: `PFError`, the envelope types, `PROTOCOL_VERSION`. If `contract` imported `protocol` to share the `ProtocolErrorCode` union, every typed client would carry the wire package and the two would version together forever. The cost of the alternative is one hand-written duplicate: `ContractProtocolErrorCode` in `packages/contract/src/infer.ts` must equal `ProtocolErrorCode` in `packages/protocol/src/error.ts`. That cost is paid by a conformance test (`packages/server/tests/protocol-error-code.test.ts`) and the five-copy checklist in the internal skill, not by a dependency edge.

### `CallInterceptor` / `CallPlugin` are duplicated in `server` and `client`

The two types are structurally identical today, so sharing them is tempting. They are kept separate because the one hard rule of the DAG is that client never depends on server and server never depends on client (a browser bundle must not pull in `runProcedure`; a server must not pull in `Link`). The only shared ancestors are `contract` and `protocol`, and neither is the right home: `contract` is types-only and `protocol` is the wire. A third "core" package for two interfaces would be the start of the plugin framework the project refuses to build. Duplication keeps the edges honest and lets the two sides diverge when they need to (server `next()` can replace `context`; client `next()` cannot).

### `@ts-pf/http` is wire helpers only

`http` owns `JsonCodec`, `RpcCodec`, the protocol header, the URL path helpers, and `httpStatus`. It does not own `FetchHandler` or `FetchLink`. That split lets `server-http` and `client-http` share the codec and status table through a package that depends on neither side, and lets `file` and `stream` wrap `JsonCodec` (and `sse` wrap `StreamCodec`) without importing a handler or a link. Putting a handler in `http` would make it a server package, and `client-http` would then depend on server code.

### `toWireError` and `isAsyncIterable` live in `protocol`

`protocol` is the one leaf that every transport package shares, so it is the only place a "thrown value → `{ code, message, data? }`" mapping and an "is this a stream of items" predicate can live without duplicating them per package or adding a DAG edge. `toWireError` owns the "unknown throw becomes `INTERNAL`, no stack, no message leak" rule for HTTP, message frames, JSONL and SSE. `isAsyncIterable` has the plain `Symbol.asyncIterator` semantics; packages that must treat a `ReadableStream` as bytes compose it (`isItemStream`) at the call site. `swr` keeps a private copy because it does not depend on `protocol` by design. `mvc-kit` gained the `protocol` edge with `taskIssues` (1.1): `bindClient` and `taskIssues` need the same cross-copy `isPFError`, a repeated brand key string was a second source of truth, and the edge adds nothing to an install (every mvc-kit consumer already has `@ts-pf/client`, which depends on `protocol`). `message-client` depends on `protocol` (as `message-server` already did) so it can use `isPFError`, `localFailure`, and `isAsyncIterable` directly instead of duck-typing `PFError` and carrying a predicate copy; its only `ReadableStream` exclusion is the same three-line `isItemStream` composition the other wire packages use.

`isPFError` must also hold across two copies of `protocol` (version skew, a bundler that inlines one). With `instanceof` alone, a typed error from the other copy fails it and `toWireError` silently sends it as `INTERNAL`. `PFError.prototype` carries a non-enumerable `Symbol.for('ts-pf.PFError')` brand, and `isPFError` is `instanceof` first (the common case costs nothing) and the brand second. The brand is on the prototype, not each instance: construction runs per failed call through the error factory, and an own property would show up in `Reflect.ownKeys` / `Object.getOwnPropertySymbols` on every error. `static [Symbol.hasInstance]` was rejected because it would change what `instanceof PFError` means for every caller and slow the common path. Every site that asks "is this a `PFError`" calls `isPFError`, never `instanceof PFError`. `mvc-kit` imports `isPFError` from `protocol`.

### `docs` keeps its `http` dependency (`A11`)

`@ts-pf/docs` imports three things from `@ts-pf/http`: `joinProcedurePath` for each procedure's `href`, `PROTOCOL_HEADER` for the catalog's `protocol.header`, and `PROTOCOL_HTTP_STATUS` for the `protocolErrors` status column. The review asked whether an `href` option could remove the edge. It cannot: the default `href` and the status table are HTTP facts that the catalog documents (the catalog is what `@ts-pf/openapi` and `@ts-pf/codegen` read, and both describe the POST JSON RPC transport), so a pluggable `href` would still need the HTTP default from somewhere and would leave the status table in place. The smaller change was chosen: no `href` option, the dependency stays, and the reason is recorded here. If a non-HTTP catalog is ever wanted, that is a new `protocol` block on the catalog, not a removal of this one.

### Fetch is an adapter; `FetchHandler` is not in `server`

The port of the server is `runProcedure` / `lookupProcedure`; the port of the client is `Link.call`. `FetchHandler` is one adapter over that port, `PortHandler` / `WsHandler` / `StdioHandler` are others. If `FetchHandler` lived in `@ts-pf/server`, Fetch would be the privileged transport and every message adapter would carry it. Keeping it in `server-http` is also what keeps `Request` / `Response` out of `server` and `client` entirely, so those packages run anywhere JavaScript runs. The same reasoning puts `FetchLink` in `client-http`, not `client`.

### One codec per handler, one per link

A `FetchHandler` takes exactly one `RpcCodec`, and the matching `FetchLink` must use the same one. Content negotiation (`Accept`, a `codecs[]` list, per-call selection) would be additive but adds a second axis to every test matrix and a class of "codec mismatch" errors that surface as confusing decode failures (review item `D13`). The default is JSON on both sides; `MultipartCodec`, `StreamCodec`, and `SseCodec` are opt-in and explicit. Negotiation is **deferred until requested** (`A10`); see the protocol items below.

### Nineteen packages; `sse` merged into `stream` at 1.0

The package count follows from three hard rules rather than from size: the client never sees server code, codecs do not pick a side, and message peers do not leak into HTTP peers. Every proposed merge breaks one of them (`server` + `server-http` privileges Fetch; `http` + `server-http` makes the client depend on a handler; `message` + `message-server` puts `runProcedure` in the client's duplex package). The review judged the split justified and recommended shared helpers over merging. The one exception was `sse` into `stream`: `SseCodec` wraps `StreamCodec`, both are HTTP-only, and an SSE user always installed both for `stream()`, so folding them costs no rule. It renames an install target, so it waited for a major and landed in 1.0. `SseCodec` and `SSE_CONTENT_TYPE` are root exports of `@ts-pf/stream` (ESM tree-shaking drops them for JSONL-only users, so no subpath), and the codec now imports `stream`'s `isItemStream` instead of carrying a copy. `@ts-pf/sse` is no longer published; its last version stays on npm, deprecated.

### `@ts-pf/mcp` is a projection plus an executor

MCP is a new paradigm (JSON-RPC 2.0 tool calls for LLM clients), and the usual rule for a paradigm is a projection like `@ts-pf/openapi`, not an adapter of `runProcedure`. MCP is the exception because a tool call must run the real procedure, with its middleware, auth, and interceptors. So the contract projects into tool definitions (names from paths, JSON Schema from `toJsonSchema`, descriptions from `docs()`), and an executor runs them: `lookupProcedure` + `runProcedure` in-process, or a typed client for a gateway. The wire belongs to the official SDK v2 (`createMcpHandler` / `serveStdio`), which builds a fresh `McpServer` per request (one instance fails under overlapping requests) from definitions computed once; passthrough schemas keep one validation pass and ts-pf's messages. No ts-pf wire handler is reused, because MCP is not ts-pf frames. The package has three entries so contract files import only `./meta` (no dependencies) and server code never reaches a client bundle. Call-pipeline options (`onError`, `maxResultChars`, and `interceptors` for the in-process form) sit on the `bindTools` executor, and `createMcpFactory(app, …)` forwards them, because they act inside `McpTools.call`, which agent frameworks also call directly. Interceptors see the procedure path, not the tool name: `McpCallInfo.tool` carries the name into `context`, so a project that wants tool-level tracing opts in through its own context type and the server core stays tool-agnostic. The `./sdk` peer floor is `@modelcontextprotocol/server` 2.3.0, not the 2.4.0 the adapter was first built on: a per-version check found every API it uses from 2.0.0, `scopeChallenge` from 2.1.0, and `requireBearerAuth({ expectedResource })`, which the OAuth docs rely on, from 2.3.0 (earlier versions ignore it, accepting tokens for another audience); the `mcp-sdk-floor` CI job keeps that true. Tests may depend on `client-http` and `server-http` (dev only) so the `{ client }` gateway form is tested over a real `FetchLink` to a `FetchHandler`. `.visible()` and `.scopes()` are hints for what a client shows and asks for, never enforcement: predicates get `McpCallInfo`, not `context`, so listing never runs the context factory, and procedure middleware stays the boundary. The design, the spikes it rests on, and the v1 / later split are in `.agents/handoff/mcp/`.

### MCP host search is pluggable; the embedding model is the app's

`$host` discovery ranks with BM25 by default: in-process, synchronous, under a millisecond, and good enough for most catalogs (about 87–90% top-5 in the design research). It misses queries that share no words with a tool ("destroy world" vs "Delete a planet permanently"), so `bindTools(toolset, { search })` takes a `SearchFactory` and the package ships `bm25Search` (default), `denseSearch`, and `hybridSearch`. The option is on the binding, not `$host`, because an embedding model is a runtime concern (keys, network, a loaded model), as `onError` is, and the toolset stays a pure definition; `createMcpFactory(app, …)` builds no hosts, so it does not take it. The embedding function is supplied by the app (`embed(texts, { kind, signal })`), so `@ts-pf/mcp` gains no model dependency: transformers.js alone brings a ~300 MB native `onnxruntime-node`, and a hosted API needs keys. `kind` exists because e5 / bge style models embed queries and passages differently. Tool vectors are embedded lazily on the first query (one memoized promise per bucket, dropped on failure so the next query retries), which keeps `bindTools` synchronous and costs nothing when nobody searches. A host holds tens to hundreds of tools, so ranking is a dot product per tool over normalized vectors; a vector database would add a service for no gain. Hybrid uses reciprocal rank fusion, which merges rank lists without making BM25 and cosine scores comparable, and falls back to BM25 (reporting through `onError`) when `embed` fails; dense-only returns an error result instead, because there is nothing to fall back to. BM25 stays the default: embeddings add a model download, cold-start load time, and per-query latency that most servers do not need.

### `@ts-pf/openapi` has an opt-in codegen profile: a richer projection, still POST JSON RPC only

Default `openapi()` output is a faithful projection of the catalog, with schemas as `toJsonSchema` produced them. That reads well in Scalar, but mainstream code generators (swagger_parser, openapi-generator, Kiota, orval) cannot use it as is. A medium-sized contract produces thousands of components, one error envelope per procedure per code, and duplicated definitions, so a team calling it from another language needs a post-processor several hundred lines long to get usable models. The default-output fixes removed what was simply wrong: nested `$schema`, closed outputs, per-host `$defs` copies, and per-procedure error copies. What remains are choices a generator wants and a human reader may not: inline envelopes; one shared `RpcError` with an `ErrorCode` enum and a `<Code>Data` schema per code; PascalCase names; every nested object hoisted to a named component; inputs closed with `additionalProperties: false` (stricter than the server, which strips unknown keys); `const` as a one-value `enum`; format regexes dropped; inferred `discriminator` mappings; and sorted keys. These sit behind `profile: 'codegen'`, which expands to individual options that can also be set alone. The default stays the plain projection, and the profile is a deliberate opt-in. The profile describes the same POST JSON RPC paths and envelopes: never GET, path params, or REST. The `streams` option (`'operation' | 'components' | 'omit'`) is part of the same decision. `'operation'` is today's `POST … application/jsonl`; `'components'` emits no path and names each stream's input and item schemas under a document-level `x-ts-pf-streams` map. A stream procedure served only over a message transport has no HTTP operation to describe, yet its item types are exactly what a non-TypeScript client needs to generate. The catalog carries no transport information, so openapi cannot tell which procedures are message-only. The option is the user's statement about the catalog they pass, and `catalog(c, { filter })` still selects procedures. This relaxes "message transports are not in this document" to "message transports have no paths in this document". Per-operation `x-ts-pf-errors` and `x-ts-pf-expand`, the document-level `x-ts-pf-streams`, and the `info` field `x-ts-pf-catalog-hash` are the package's only `x-` extensions; generators ignore unknown extensions. `enumNames` (naming shared inline enums by value set) is an option the profile never sets: matching by values is a heuristic that can join unrelated enums, so `.meta({ id })` stays the recommended way to name one. The hash is passed in as an option because `catalogHash` lives in `@ts-pf/codegen` and uses `node:crypto`. `@ts-pf/docs` stays runtime-neutral, so only `canonicalize` moves there: the profile's `canonical` output and `catalogHash` then sort keys the same way. Hoisting, dedupe, and naming stay internal to openapi until a second consumer (a non-TypeScript generator) needs them in `@ts-pf/docs`.

### Other languages get a spec, fixtures, a codegen profile, and a guide; no first-party clients

ts-pf servers are called from Dart, Swift, Kotlin, Python, and Go apps. The project supports those callers with four artifacts it already keeps correct: `PROTOCOL.md` (written for implementers in any language since revision 1.2), the `conformance/` fixtures (replayed by the TypeScript clients in CI), the OpenAPI codegen profile (models from each platform's own generator), and `docs/other-languages.md` (pseudocode for the transport, response classification, error mapping, streams, and drift checks). It ships no runtime, client library, or generator template for another language. Each would be a second implementation of the wire to keep in step with every revision, tested in a toolchain this repository does not run, released on another ecosystem's cadence, and tied to an HTTP or JSON library its users may not want. The transport a client needs is small (about 100–200 lines for HTTP), and the fixtures let its authors prove it without a maintainer. Generated REST clients are not the answer either: they read the outcome from the HTTP status, the classification error revision 1.2 was written to prevent, so the guide and the openapi docs say "models only". A community client lives in its own repository and proves itself with the fixtures. Hoisting, dedupe, and naming stay internal to openapi (above) because no in-repo non-TypeScript generator will need them.

### No Node `IncomingMessage` adapter, no framework adapters

`FetchHandler` speaks the Fetch `Request` / `Response` pair, which Workers, Bun, Deno, Hono, Next.js, and Astro all hand you directly. A Node `http.createServer` bridge is a few lines of userland code that `@hono/node-server` and `srvx` already maintain well. Shipping one here would commit the project to tracking Node streaming semantics (body backpressure, `duplex: 'half'`, trailers) for every release, and would make a framework-shaped adapter the "real" API. The README section "Serving FetchHandler" points at the userland bridges; `@ts-pf/astro` is the one opt-in integration, and it exists because Astro's `APIContext` and `Astro` global need a context function, not because Fetch is missing. Because the bridges are the supported path, `server-http` must work with the Request-shaped objects they pass, not only undici's. srvx's lazy Node request passes `instanceof Request` but undici cannot clone it, so a plugin that rewraps the request (`RequestLimitPlugin`) builds the new one from the URL, method, headers, and signal instead of `new Request(request, init)`, and needs no srvx `patchGlobalRequest()` (`srvx/node`).

### Cacheable GET reads and public REST stay userland (for now)

Every call is a POST, so a CDN or browser cannot cache a read by URL, and third parties expecting REST get RPC paths. Neither mattered to the apps ts-pf was built for, and client-side caching (`CachePlugin`, `DedupePlugin`, `@ts-pf/swr`) already covers in-app reuse. Both gaps close in userland without a wire change: `HandlerPlugin.onRequest` runs before the method check, so a bridge can turn `GET {prefix}/{path}?input=<JSON>` into the POST `FetchHandler` serves (and set `Cache-Control` in `onResponse`), and a `FetchInterceptor` on `FetchLink` can send it; a REST facade is a userland router calling `createLocalClient(app)`, so middleware and typed errors still run. `examples/plugins` carries the smoke-tested bridge, and the `ts-pf-server-http` / `ts-pf-openapi` skills document it. The bridge is opted in per procedure through contract meta (`.meta({ http: { method: 'GET', cacheControl } })`), never handler-wide, because a GET runs from a plain cross-site link with cookies and must not reach a procedure that writes. It stores nothing it should not: errors and responses carrying `Set-Cookie` get `no-store`, and a `Cache-Control` the call set itself wins over the meta default. The client half drops `x-ts-pf-protocol` on the GET (absent is accepted) so a cross-origin read is a CORS simple request. The `?input=` wire and the `http` meta key are chosen to be exactly what a first-party binding would ship, so moving to it changes no contract and no URL. **Deferred** to a protocol revision 1.3 when a deployment needs CDN or shared-cache hits for reads: an `http()` meta helper and `?input=` codec helpers in `@ts-pf/http`, a GET branch in `FetchHandler` gated on that meta (lookup before the method check for GET, `no-store` on failures), a `FetchLink` `method` predicate (GET without `x-ts-pf-protocol`) with POST fallback for non-JSON input and long URLs (the client has no runtime contract, so it cannot read meta itself), `http` lifted onto catalog entries, and a `get` operation in `@ts-pf/openapi` (relaxing the POST-only lock for that one binding, still no path params). The HTTP `QUERY` method (RFC 10008) waits for CDN support. A REST package, if ever wanted, would follow `@ts-pf/mcp`: a projection plus an executor beside `FetchHandler`, never inside it.

### Catalog diff lives in `codegen`, is direction-aware, and treats output enums as open

`diffCatalog` sits next to `catalogHash` because both read committed `catalog.json` and neither belongs in `@ts-pf/docs` (which produces catalogs, not policy about them). A change is judged from an old client's side: inputs are what it sends (narrowing breaks), outputs and error `data` are what it receives (widening breaks). One exception is deliberate: a new output enum value or union variant (and a new output property or error code) is **safe**. Treating them as breaking would make every additive feature a major change and push teams to disable the check; the cost is that clients must tolerate values they do not know (a `default` branch, an unknown-variant fallback), which the guides state. A change of type, `null`, or looser bounds in output stays breaking, because no reasonable client tolerates a number where it reads a string. The walker models a small keyword set; anything else (`pattern`, `prefixItems`, `allOf`, …) is a safe `unknown-change`, never breaking, so the check has no false failures from keywords it cannot reason about. It flags known breaks; it does not prove compatibility. `compare` / `breaking` / `compat` are not alternative names: one function, one name.

### `openapi()` normalizes schemas; `catalog()` does not

Code generators (openapi-generator, Kiota, orval, swagger_parser) make one model per component, so `openapi()` hoists root `$defs` into `components.schemas.<id>`, shares one `Error.<CODE>` per declared code when every `data` shape matches, and drops nested `$schema`. It also drops `additionalProperties: false` from output and error `data` schemas: a closed output makes a generated client reject a field a newer server adds, which turns every additive server change into a breaking one. Input schemas are left as the catalog gives them (a strict object is the server's promise to reject unknown keys; a plain object's stripping is not something a client should lean on either way; closing every input is the opt-in `closeInputs`), and the `{ ok, … }` envelopes stay closed because the protocol defines them. When an id's input and output shapes differ, the output keeps `<id>` and the input is `<id>Input`; same-side conflicts throw rather than pick a winner, because a silently merged model would be wrong for one of the procedures. These are normalizations of the document only. `toJsonSchema` and `catalog()` keep the converter's schemas unchanged, because `@ts-pf/mcp` builds tool schemas from them (a model should see closed objects) and `catalogHash()` hashes them (a normalization change must not invalidate every generated client). Zod's `__schemaN` defs are named per conversion, so they are not ids: they stay per host (`<host>.__schemaN`) and are shared only when identical.

## Runtime behaviour

### Callers are typed with the input schema's input; handlers with its output

`.input(S)` stored one type, `InferSchemaOutput<S>`, and both the client and the handler read it. A field with `.default(x)` was therefore required in `client.posts.create(...)`, although the wire accepts it missing and `docs/evolution.md` tells servers to add fields that way; a `.transform()` input asked the caller for the transformed type. The catalog already used `io: 'input'`, so codegen clients were right and builder clients were not. `ContractProcedure` now carries both: its first parameter is what a caller sends (`InferSchemaInput<S>`, the same type codegen emits), and a fifth, `TParsedInput`, defaulting to the first, is what the handler and `.useAfter()` receive. The default keeps hand-written and generated `ContractProcedure<I, O>` types valid, and makes them describe both sides. Output keeps one type: output checks default off, so the client receives what the handler returned, and typing the handler's return with the output schema's input would let it return a value the client is not promised. `stream(item)` splits the same way per item. Type-only; no runtime or wire change.

### Expandable outputs: the output schema stays wide, `.expand()` narrows the caller

A read that takes `populate: ['authorId']` returns `authorId` as the target document, otherwise as its id. With one call signature per procedure, every client typed that field as the union, and the workarounds were wrong in other ways. Separate `getPopulated` procedures multiply with every combination, a union input is one call signature, not overloads, and a hand-written client type that is generic in `populate` is lost the moment the client passes through `createSwr`, `bindClient`, or codegen. A downstream CMS asked for it. Stripe's `expand[]`, JSON:API's `include`, and Strapi's and Payload's `populate` show how common the pattern is. `.expand({ key, at?, fields })` records it on the contract, and `ProcedureClient` becomes generic in a `const` tuple of field names when a procedure has one.

Four choices shape it. **The output schema is the wide one** (each field in either form), and `fields` hold the expanded schemas, so a field's plain type is the wide type minus the expanded one. The alternative was a plain output with `fields` replacing parts of it. That would leave no schema for what the server actually sends: the handler's return type, opt-in output validation, OpenAPI, and MCP would all describe a narrower value than the wire carries, and Standard Schema cannot compose a wide schema at runtime. With the wide schema, none of those change, and nothing changes on the wire either. The list is an ordinary input field. A field whose plain type is only `undefined` exists only when expanded. An optional list such as `categories?: Link[]` is absent without the list and required with it. **It is data, not a type function.** `codegen` prints `.d.ts` from the runtime catalog, so the expansion has to live in `~pf.expand` and `CatalogProcedure.expand`, and the 6th `ContractProcedure` parameter, `Expansion<Key, At, Fields>`, has to be something a printer (or a hand-written mapped contract type) can write. So `Fields` holds output types, not schemas. **`at` is a key tuple** (`['docs']`, with arrays and `null` passed through), not a path string such as `'docs[]'`: the types, the catalog, and OpenAPI would otherwise each parse a mini-language. **A list that is not a tuple gives the wide output.** A variable typed `K[]` could be empty at runtime, so narrowing it would be unsound.

Limits, on purpose. There is one expansion per procedure, field names are flat (no nested population such as `author.org`), and the handler is not narrowed per call: it returns the wide type, and populating only what was asked is the app's contract. `@ts-pf/swr`'s callable and `.call` narrow, but `useSWR(key, fetcher())` cannot, because SWR infers data from the fetcher, which never sees the key's list. Passing a fetcher that calls the procedure narrows it, and `InferExpandedOutput<T, P>` names the type for any other case. OpenAPI carries `x-ts-pf-expand` with the field names only, since the expanded schemas are already in the wide response. Generators for other languages see the wide schema. `diffCatalog` judges an expansion from the caller's side: losing it, renaming its `key`, moving it (`at`), or losing a field is breaking, and adding one is safe.

### `validation.output` defaults off; `onError` defaults to logging

Input validation is the contract's promise to the handler and runs by default. Output validation is a check on the server's own code, costs a schema walk per response, and would be paid on every call forever; it is opt-in (`validation.output: true`). When it is on and fails, the client receives `INTERNAL` with no issues, because the bug is on the server and the schema's issues would leak internals. The companion decision (`Q3`, review `D4`) is that an unknown throw and an `INTERNAL` `PFError` are logged with `console.error` when no `onError` is given. Silence by default was the earlier behaviour and meant the first production incident was invisible; tRPC and oRPC users expect a log line. Passing `onError` replaces the default logging rather than adding to it, so a real logger is never duplicated.

### A stream procedure on a non-streaming codec is `BAD_REQUEST`, not a 200

`JsonCodec` stringified whatever a handler returned, so a `stream()` procedure served by the default `FetchHandler` answered `200 {"ok":true,"output":{}}` and its iterator was never closed. Two guards replace that. `RpcCodec.streams` is an optional capability flag (`false` on `JsonCodec` / `MultipartCodec`, `true` on `StreamCodec` / `SseCodec`); on `false`, `FetchHandler` checks the contract after lookup and answers `BAD_REQUEST` before the body, context, or middleware, through the same error path as 404 / 405. The flag is read once per handler, so the pre-check costs two property reads per call, on non-streaming codecs only. The brand is `stream()`'s `'~pfStream'` key read inline, because `server-http` must not depend on `@ts-pf/stream`; `@ts-pf/docs`' vendor check is not reused, since `@ts-pf/mcp` passthrough schemas share that vendor. A codec that leaves the flag unset, or a handler that returns an `AsyncIterable` its contract does not declare, is caught after the handler returns: an `AsyncIterable` output that was not encoded as a `ReadableStream` is closed with `return()` and gets the same error (one `isAsyncIterable` test per successful response, skipped for a codec that declares `streams: true`, whose encoding is trusted). Both are `BAD_REQUEST`, not `INTERNAL`, because the answer is about the endpoint: this call asks for a stream that this endpoint's encoding cannot deliver, and the client fixes it by using a streaming codec, so the pre- and post-dispatch cases give the client one error to match. Like other `BAD_REQUEST`s it is not logged by default; `onError` sees it. The flag is optional so existing custom codecs keep compiling.

### Middleware narrows context (`Q4`, resolved at 1.0)

Through 0.x, `.use()` middleware runtime-merged what it passed to `next({ context })` but did not widen the type the handler saw, so `requireUser` left `user?: User` optional and handlers narrowed with a checking helper (review `D10`, "the single lock with the largest DX cost"). It waited for context branding (`Q7`), because widening the type changes `createImplementer`'s generics where they meet `impl.router()` completeness checks, nested slice apps sharing one `AppCtx`, and `createLocalClient`'s context argument. With branding in place, 1.0 splits the context in two. `TCtx`, from `$context<C>()`, is what adapters supply; it alone brands `ImplementedProcedure` / `ImplementedRouter`, so completeness checks, slice nesting, and every adapter are unchanged. `TCurrent`, a third parameter of `Implementer` and sixth of `ProcedureBuilder`, is what middleware and handlers below a level see. `next({ context })` resolves to `MiddlewareResult<TAdded, TOutput>`, the output at runtime carrying the added keys as an optional phantom symbol property; `use()` / `useAfter()` infer `TAdded` from the middleware's return type and continue with `MergeContext<TCurrent, TAdded>` (added keys override, as the runtime spread does). Three details make it hold: `NoInfer` on the result's `TAdded`, or a bare `next()` would infer its added keys from the middleware's own unresolved return type and collapse to `never`; `next`'s `context` intersects each key `TCurrent` already has, so an added key may narrow (`user?: User` → `User`) but not change type, which keeps the old `Partial<TCtx>` safety; and a key added on only some paths is inferred from the union of returns, so it stays optional. The cost is that a middleware must return `next()`'s result, spread if it changes the value (tRPC and oRPC require the same), and that narrowing follows the builder: only handlers built from the narrowed level see the keys. A runtime-wrapper design (`next()` returning `{ output, context }`, as oRPC does) was rejected because it would change every middleware body and the output that `mapStreamErrors(await next())` wraps, for no type gain. Building handlers from a narrowed level made one runtime gap visible: `authed.router({ x: authed.x.handler() })` prepended `authed`'s middleware to a procedure that already carried it, so it ran twice; `router()` now skips a chain the procedure already starts with.

### Handler `signal` stays optional

The typed handler opts keep `signal?: AbortSignal`. `FetchHandler` passes `request.signal` and the message handlers pass a per-call signal, but `createLocalClient` without `{ signal }`, a direct `runProcedure`, and `@ts-pf/mcp` without a host signal pass none. Making it required meant `runProcedure` allocating a fresh `new AbortController().signal` per call when none was given (one shared never-aborting signal was ruled out: listeners handlers add to it would accumulate for the life of the process). Measured with `npm run bench` (eight runs each, interleaved), local unary went from a median of ~1.86M to ~1.77M ops/s, about 5% and slower in every pair, above run-to-run noise; local declared error did not move. The hot-path cost buys a type change only, so the server skill and README document the guard instead (`signal?.throwIfAborted()`, `signal ?? AbortSignal.timeout(ms)`). Revisit if a cheaper way to supply a signal appears.

### Middleware `next()` is single-call; middleware maps domain errors

A `.use()` / `.useAfter()` `next()` runs the rest of the chain on the execution's shared `input` / `ctx` (the input check replaces `input` with the parsed value; `next({ context })` merges into `ctx`), so a second call re-runs inner middleware on the first run's state (a second `.use()` call re-validates already-parsed input), inherits context inner middleware added, and races when concurrent. Server call interceptors already give each `next()` a fresh execution (`A7`), so retries and hedging live there; middleware is documented as single-call rather than guarded, because a guard is a per-call cost for a misuse the docs can steer. Error mapping is the opposite case: it belongs in middleware, not in an interceptor, because middleware runs inside `runProcedure` before `finalizeDeclaredError`, so a mapped declared error still gets its `data` checked and its declared `status` filled when it has none (not its `message`: the mapper sets that). A stream throws after `next()` has returned, so `mapStreamErrors` (a hand-written iterator wrapper, since an async generator's `return()` before its first `next()` never reaches the source) covers the mid-stream half of the same middleware.

### Astro context resolves inside `FetchHandler`

Through 1.0.1, `createAstroHandler` awaited its context function before calling `FetchHandler.handle`, so a `PFError` the function threw to refuse a request (`UNAUTHORIZED` / 401 for a bad token, `FORBIDDEN` / 403 for a non-member: the usual edge check) escaped to Astro as a 500 instead of the encoded error, and the function also ran (session and membership lookups) for prefix misses, 405s, and unknown procedures. Three downstream apps worked around it by calling `FetchHandler` directly. `createAstroHandler` now passes the function to `handle()`, which resolves it at step 3 inside its error path, the same as any `FetchHandler` context factory. That is a patch, not a major: the package is documented as a thin shell around `FetchHandler`. The cost is that the function now runs after the body decode, so it cannot read the body (raw-body checks go in a `HandlerPlugin.onRequest`) and a malformed body is a 400 before an auth refusal. `createAstroLocalClient` keeps resolving first: there is no wire, so a throw rejects the call and the page handles it.

### Client `DedupePlugin` default key covers mutations (`Q2`)

`new DedupePlugin()` keys every unary call by `JSON.stringify([path, input])`, so two concurrent `create({ name })` calls coalesce into one request (review `D5`). The plugin behaves as documented; the mistake was presenting it in the README happy path without the hazard. Option (a) from the review shipped: the bare constructor is out of the happy path and every place that introduces the plugin says to pass `key` to restrict it to reads (`examples/plugins/src/read-key.ts`). Option (c), a `reads` / `idempotent` option that makes the bare constructor a type error, is planned as a minor release; option (b), requiring `key`, was rejected because it breaks existing users for a problem a type-level nudge solves. `CachePlugin` has the same default and gets the same treatment.

## Errors and status

### `isLocalFailure` is `local === true`, not `status === 0`

A local failure (network error or abort on any link) is the client's own `PFError` with `code: 'INTERNAL'` and `local: true`, built by `localFailure()`, which today also stamps `status: 0`. That `0` is a placeholder, not a protocol status: nothing on the wire carries it, a non-RPC HTTP response is *not* local and keeps its real HTTP status, and once `status` becomes optional (below) local failures will simply have none. A check on `status === 0` would therefore break on the next change, while `local === true` says exactly what happened. `toJSON()` omits `local` for the mirror-image reason: it never crosses the wire, so a server can never make a client think a failure was local.

### `status` is transport-only; `PFError.status` is optional (`Q1a`)

The discriminator is JSON `error.code`. HTTP status is derived from it by `httpStatus()` in `@ts-pf/http` and is never put in the envelope, so a message peer and an HTTP peer agree on the error without agreeing on a status table. The review found that a required `status: number` on `ClientError` lied: 404 over HTTP, a synthesized 400 over WebSocket and MessagePort, 200 mid-stream, 0 locally (`A1`). **Decided and shipped** (`Q1a`): `PFError.status` and `ClientError.status` are optional with no default; `httpStatus()` applies the 400 default at the HTTP edge; `errorFromEnvelope` and the stream/SSE codecs no longer synthesize one; `ErrorDef.status` stays as optional HTTP and OpenAPI metadata; `localFailure` keeps `status: 0` with `local: true`; `@ts-pf/mvc-kit` fills `400` before handing an error to mvc-kit, which needs a finite number. The per-transport table lives in `PROTOCOL.md` and the client skill. Switch on `code`; treat `status` as transport metadata. Later extension, not a reversal: `runProcedure` applies the same `ErrorDef.status` stamping at the point of throw (middleware or handler, not a call interceptor), so a hand-built `new PFError({ code })` for a declared code (no `status` of its own) leaves with the declared status and keeps its `cause`, exactly as `errors.X()` would have; `status` is still not on the wire, and a mid-stream throw still cannot change the HTTP status because the 200 is already sent.

### `METHOD_NOT_ALLOWED` stays in the closed set

Only `FetchHandler` emits it (a non-POST under the prefix), but it is a protocol code rather than a Fetch-only status because non-TypeScript clients switch on `error.code` and must be able to recognise it without a side table. `PAYLOAD_TOO_LARGE` is shared between the HTTP body cap and oversize message frames for the same reason. Adding a code means editing `ProtocolErrorCode`, the contract duplicate, `PROTOCOL_HTTP_STATUS`, and `PROTOCOL.md` (the docs catalog derives from the first and third; only its `VALIDATION` data branch may need a touch), which is why the set is closed and `.errors()` may not redeclare these codes.

## Message transports

### No `TransportHandler`, no `HandlerPlugin` on message transports

`FetchHandler.handle(request)` and `PortHandler.bind(port)` have different shapes on purpose. A common `TransportHandler` interface would need a lowest-common-denominator request object, and that object would be HTTP-shaped, because HTTP is where headers, methods, and bodies live. `HandlerPlugin` (`onRequest` / `onContext` / `onResponse` / `onError`) is built around `Request` / `Response` and CORS preflight; porting it to a frame-based session would mean inventing fake requests for frames. What message adapters share with `FetchHandler` is the call pipeline, so the shared surface is `CallInterceptor` on `HandlerOptions.interceptors` and `validation`, not an HTTP plugin interface. Reusing `RpcCodec` as a frame codec is refused for the same reason: frames have no content type. `DuplexHandler` / `DuplexLink` (`@ts-pf/message-server` / `message-client`) are not a `TransportHandler`: they are generic only over `@ts-pf/message` `Duplex` — the same JSON text frames, handshake, and multiplex rules behind `PortHandler` / `PortLink` — so a new pipe supplies four functions (`send` / `onMessage` / `onClose` / `close`) and nothing about requests, headers, or methods crosses over from Fetch.

### `Duplex.send` is drain-aware; slow-peer protection is on by default (`A8-B1/B2/B3`)

Before this change every `Duplex` adapter's `send` returned `void`, `PushQueue` was unbounded, and `emitStream` wrote as fast as the iterator yielded, so a slow WebSocket or stdio consumer grew server memory without bound and a client `break` reached a server whose generator had already finished (review `A8`; measured: a 100k-item stream to a stalled consumer finished producing in 80 ms and cost +28 MB heap / +150 MB RSS). What shipped is the proposal's design B with the maintainer's direction to err on the side of the server: `Duplex.send` is `void | Promise<void>` (a promise means "above the write high-water mark"; it must settle on close, and a rejection closes the session), `Duplex` has optional `pause` / `resume`, `MessageSession.send` stays synchronous and surfaces the promise as `SendResult.drained`, and only senders with a successor frame on the same id (`item`, `in-item`) await it, so the unary path and `onHello` gain no await. The stdio adapter honours `write()` / `'drain'` and `input.pause()`; the WebSocket adapter polls `bufferedAmount` every 10 ms against `highWaterMark` and forwards the socket's own `pause` / `resume` when it has them (npm `ws`); the port adapter reports nothing because a `MessagePort` has no buffer signal and cannot stop receiving, which is recorded as a limitation rather than papered over with a JS-side buffer that would only move the memory. Receive queues (`createPushQueue({ highWaterMark, onPause, onResume })`) are bounded in frame text length and pause the duplex connection-wide while any queue is over the mark; they never drop, because a dropped frame is a protocol violation and a rejected call would kill legitimate slow-but-progressing consumers. Third-party duplexes keep compiling: `void` is assignable to the widened return type, and a duplex that returns nothing and has no `pause` simply gets no protection on that pipe. HTTP JSONL and SSE are pull-based and unaffected. After the change the same experiment over the memory duplex and over a stdio pair parks the producer at a few thousand items (+1.5–2.4 MB heap), finalises the generator exactly once, and ends the stream with the drain error below.

### Protection is on by default, with one option object and a drain timeout that aborts the call, not the connection

The maintainer's rule was that a server must not accumulate resources because one client reads slowly, and must not hold a handler suspended forever for a client that never drains. Both bindings therefore take the same flat `BackpressureOptions` (`HandlerOptions.backpressure`, `LinkOptions.backpressure`): `highWaterMark` 1 MiB, `drainTimeout` 30 s, `onStall` one `console.warn` line for `aborted` only. A `paused` is still delivered to a custom hook but not logged by default, because a pause is normal flow control: it fires once per large stream on any healthy link and a busy WebSocket server would otherwise log forever. `onStall` is observability only: the waiter settles the call's outcome first and then notifies inside a `try`, so a throwing logger can neither hang the call (the review found the `aborted` path could leave a call parked with its `inflight` entry) nor turn a stall into an `onError` / `INTERNAL` result. The escape hatches are spelled once each (`Infinity` unbounds, `0` waits forever, `false` silences) and a bad value is a `TypeError` naming the option from the constructor, including `WsLink`, whose `DuplexLink` is only built on `open`. When the timeout fires on the server, that call alone is aborted: its `AbortSignal` fires, the iterator's `return()` runs once (the generator is parked at a `yield`, so `finally` / cursor cleanup runs immediately instead of after full production), its remaining frames are dropped, and the peer receives a terminal `result` with `INTERNAL` and the fixed message `Peer did not drain within <n> ms` if the socket still accepts it. The connection stays open because other ids on it may be healthy and the Multiplex rules already guarantee they complete independently. It is deliberately `INTERNAL` with a fixed message rather than a new protocol code: the closed set exists so non-TypeScript clients can switch on it, and a drain timeout is an operational condition on the server, not something a client can act on differently from any other server-side failure; `PROTOCOL.md` documents it under "Backpressure" as a server-side condition. It is reported through `onStall({ action: 'aborted' })` and never through `onError`, because `onError` means "the handler threw" and a slow peer is not a bug in the handler. The client mirrors it for input streams: `localFailure('Peer did not drain within <n> ms')`, a `cancel` if the socket accepts it, and `iterator.return()` once. The `onStall` payload is `{ path, id, waitedMs, action }`; the proposed `bufferedBytes` field was dropped because the `Duplex` contract has no buffered-amount accessor and widening it for a log number was not worth it. The known cost is head-of-line blocking: a paused receive side holds every id on that connection, the HTTP/1.1 trade-off, which is why the credit-window design that bounds the sender per stream stays the protocol 2 answer.

### `onHello` is the context factory; `runProcedure` is not awaited in `onFrame`

Context is created once per connection in `onHello` (or per `bind()` for `context: (info) => ctx`), not per frame, because a connection is the unit of authentication for a socket and because a per-frame factory would run on every `call`, `cancel`, and stream item. `MessageSession.onFrame` must return without awaiting `runProcedure`: awaiting it would serialise calls on one connection and make a single slow procedure block every other in-flight call and every `cancel` frame.

## Protocol 1.1 design spike

These come from the protocol 1.1 design spike (maintainer notes, see the top of this file). The governing fact is that the protocol 1 `hello` / `hello-ok` handshake rejects unknown keys, so nothing in protocol 1.x can advertise a capability during the handshake without breaking 1.0 peers; only `hello.meta` and HTTP headers are tolerant channels.

### Deferred to a later revision

- **A8-B1/B2/B3, drain-aware `Duplex.send`, bounded `PushQueue` with `pause` / `resume`, one `BackpressureOptions`** — **shipped** (see "Message transports" above); no wire change.
- **A8 follow-up, a hard receive ceiling for non-pausable duplexes** — deferred: abort the one input-streaming call when its queue reaches a multiple of `highWaterMark` (e.g. 4×) on a duplex with no `pause`, so a flooding client cannot grow a Bun / uWebSockets.js / Deno server; must land before any non-`ws` server adapter is documented.
- **A8 follow-up, `maxInflight` per connection** — deferred: nothing bounds the number of concurrent `call` frames one connection may open; a per-connection cap that answers the excess with a terminal `result` error is the matching knob.
- **A8-A, a `credit` frame with a handshake-negotiated window** — deferred to protocol 2 because the handshake cannot carry the negotiation in protocol 1.x; it is the only backpressure design that bounds the *sender* per stream rather than the adapter, and the only one that removes the connection-wide pause on `MessagePort` and browser WebSocket. A protocol 1.x receiver ignores an unknown frame type with an in-flight id, so a `credit` frame is harmless to it, but one for a terminated id draws `BAD_REQUEST`, so the protocol 2 design must never send credit after a terminal frame.
- **A9 (client side), per-call `meta` on `Link.call`** — deferred until requested. It does not need a package major: an optional fourth parameter after `signal` is additive for callers and for custom `Link` implementations (fewer parameters still conform), so it is a package minor. Replacing `signal` with an options object would be a package 2.0 and is not planned. The server-side tolerant reader (accepting an object-typed `meta` on `call`) is a protocol 1.x additive change and can land first.
- **A10, codec negotiation (`RpcCodec.contentTypes`, `encodeSuccess(output, { accept })`, `FetchHandler({ codecs })`, `FetchLink` sending `Accept`)** — deferred until requested; additive and header-only, but it reintroduces the mismatch class that one-codec-per-handler avoids. The `Accept` advisory paragraph in `PROTOCOL.md` landed with the A2 version-header rule (below).
- **Token rotation on a live connection** — deferred: the credential is fixed at hello; rotating it without reconnecting would be a later additive frame.

### Shipped in revision 1.1

- **A2, version header read on HTTP; one version source** — `FetchHandler` reads the request `x-ts-pf-protocol` (absent → accept; present and not `1` → `400 BAD_REQUEST` `Unsupported protocol version`, the message handshake's string, after the method check and before procedure lookup and the body) and `FetchLink` rejects a response whose header is present and not `1`, body unread, with `INTERNAL` + the HTTP status + `Unsupported protocol version (x-ts-pf-protocol: <value>)` + `cause` = the `Response`. That failure is deliberately **not** local: `isLocalFailure` means "the request never reached the server", a response carrying `x-ts-pf-protocol: 2` demonstrably did, and a local failure would make `RetryPlugin`'s default predicate retry a deterministic mismatch. It is the same shape as the non-RPC decode failure. `PROTOCOL_MAJOR = 1 as const` in `@ts-pf/protocol` is the single source; `PROTOCOL_VERSION` is its string (still the value inside `catalog()` / `catalogHash()`), and `@ts-pf/message` uses the constant for `v`. Wire bytes of accepted calls are unchanged; `PROTOCOL.md` gained the "Revisions" and "Content negotiation" paragraphs and its title now carries the revision. The only stricter case is a non-ts-pf client sending any value other than `1` (`1.0`, `2`, empty), which no shipped client does.
- **A7, per-execution state in `runProcedure`** — each time the innermost interceptor calls `next()`, `runCallInterceptors` calls `execute(state)`, which builds a fresh `Execution` object and runs the `.use()` / input check / `.useAfter()` / handler chain through module-level functions that take it as a parameter, so an interceptor that calls `next()` twice concurrently gives each run its own `input` / `context` / `signal` instead of racing on three variables shared across the whole `runProcedure` call. `runCallInterceptors` already built a fresh state per `next()`; the fix only moved the chain to match (first as a closure per execution, then as the `Execution` object so a run allocates one object instead of a closure per step). Sequential `next()` behaves exactly as before; the empty-interceptor fast path is still a length check. Hot-path rule that came out of it: the per-call path (`runProcedure`, call interceptors, event helpers, the error factory, `createClient` / `createLocalClient` proxies) builds objects with their required keys and assigns each optional key only when present, never through `defined()` or a conditional spread; `createErrorFactory` is memoized per error map and the shared factory is frozen; `npm run bench` (`scripts/bench.mjs`) is the regression guard, run before and after any change on that path.

### Shipped in revision 1.2

- **Revision 1.2: the spec is written for implementers in any language** — Revision 1.1 described much of the wire through the TypeScript client. The non-RPC response rule sat in a paragraph about `FetchLink`, and TypeScript conventions (`local`, `status: 0`, `PFError`) were mixed into MUST-level frame rules. A client written in another language from that text could easily classify a proxy's HTML 404 by its HTTP status and treat it as an application outcome ("no access"), with destructive results. Revision 1.2 is the clarity pass. It adds a normative "Classifying an HTTP response" section, RFC 2119 keywords, one-screen HTTP and WebSocket client checklists, a "TypeScript reference client" appendix holding the TypeScript-specific behaviour, reserved close-code ranges (4900–4999 for the protocol, 4400–4499 recommended for apps), a non-normative reconnecting section, a recommended `hello.meta.authorization` key, `hello-error` from a thrown `PFError` (below), and `BAD_REQUEST` for a stream procedure called on an endpoint whose codec cannot carry streams. The normative text matches what the TypeScript client and server already do, so no 1.1 implementation becomes non-conforming. Checks stricter than `JsonCodec` (an object `error` with string `code` / `message`) and status-class retry are SHOULD / MAY. The cacheable GET binding previously earmarked as 1.2 (above) moves to revision 1.3, unchanged.
- **`hello-error` carries a `PFError` thrown by `onHello`** — Until revision 1.2, any throw from the per-connection context factory became the fixed `hello-error` `INTERNAL` / `Internal server error`. A server could not tell a client why it refused a connection: an expired token, a banned account, and a crashed database all looked the same. The only way left to say more was an app-private close code. The fixed literal existed to keep factory messages (stack traces, SQL errors) off the wire. `toWireError` already gives that guarantee for every handler throw: a `PFError` is the server's deliberate, client-facing error and goes out as `{ code, message, data? }`, and anything else becomes `INTERNAL` with the fixed message. Revision 1.2 applies the same mapping to `onHello`. The `@ts-pf/message` session passes the thrown value through `toWireError` into `hello-error`. So `throw new PFError({ code: 'UNAUTHORIZED', message: 'Session expired' })` reaches the client as that code, and an unknown throw still produces exactly the old literal. No frame, key, or code changes. `hello-error.error` has always allowed any code and `data`, and a 1.0 client already fails the connect with whatever error it receives. The change is therefore additive under the Revisions rule. It is a behaviour change for servers that already throw a `PFError` from `onHello`: its message now reaches the client, which is what a `PFError` means everywhere else. The WebSocket bind handle gains `close(code?, reason?)`, and `WebSocketLike.close` takes an optional `reason`. An app can then close a live connection with an application close code after hello. The socket is closed with that code before the session tears down, so the duplex's own `1000` does not win. Port and stdio handles keep `close()`: neither pipe has close codes.
- **Conformance is versioned JSON fixtures, not a reference server** — A spec written for implementers in any language needs a way for those implementations to prove they follow it. `packages/protocol/conformance/` holds plain JSON test vectors (`http.json`, `http-stream.json`, `ws.json`) and a `README.md` that says how a runner replays them: an HTTP case is a request the client must send plus a response it must classify; a WebSocket case is a frame script from the client's side. A runner needs only its own client and a fake transport, so a client in any language runs them in its own test suite with no server, no network, and no Node process. A listening reference server was rejected: it would need a process to manage in every other language's CI, a WebSocket server (the project does not depend on the `ws` package), and it could only test what a well-behaved server sends, while the fixtures deliberately include malformed responses and frames. The files are data, not schemas, so "no schemas in `protocol`" holds; they ship through `files`, carry `protocol` and the `revision` of `PROTOCOL.md` they were written against (a test keeps both equal to the spec), and cite the section each case checks. The TypeScript clients replay the same files in CI, so the fixtures and the reference client cannot drift; a fixture that the TypeScript client fails is a client bug or a spec question, never a fixture to edit until it passes. `@ts-pf/protocol/conformance` re-exports them typed through a JSON import (`with { type: 'json' }`), which is why protocol's tsconfigs set `module: Node20` and `resolveJsonModule`; the JSON stays the single source.

## Process

### Changesets, `latest` only, no pre-release mode

Every published package change carries a `.changeset/*.md` so the changelog is written by the person who made the change, in the PR that made it. Publishing only to the `latest` dist-tag and refusing `changeset pre enter` keeps one release channel: consumers track the newest version of their major; a `next` channel would double the support surface for no users today. A major is announced through its changeset and CHANGELOG, not a pre-release.

### One version for every published package

Every published `@ts-pf/*` package is in one Changesets `fixed` group, so they release together on one version; the first unified release is `0.5.0`. Before, versions drifted per package (0.1.x to 0.4.x at the time), and a consumer could not tell which versions belong together. One version makes "every `@ts-pf/*` at X" the check, and a mismatched set is visible at a glance. The cost is a version bump, and an unchanged republish, of every package on every release, and a break in any one package takes them all to the next major ("Semver from 1.0"). The fixed group is an explicit list (globs would also match the ignored private examples); `check:deps` asserts that it lists exactly the published packages.

### Internal dependencies are caret ranges floored at the release

A published package declares each internal `@ts-pf/*` dependency as `^` plus the version released with it (`"^1.2.0"`). Two copies of a shared package break TypeScript compatibility of classes with private members (`FetchHandler`) and any raw `instanceof` (`isPFError` survives through its brand, but a duplicate is still dead weight), so the ranges must let npm settle a consumer's set on one copy even when it drifts, e.g. when Dependabot bumps one package: `client@1.0.0` asks for `protocol ^1.0.0`, `server@1.1.0` for `^1.1.0`, and `protocol@1.1.0` satisfies both. Exact pins, the rule through 0.x, nest a second copy in that case; they were kept before 1.0 because a `^0.x` range does not cross a minor, so consumers had to move every package together anyway, and an exact pin at least named the tested set. The cost of a caret is that a package may run with a newer sibling minor than it was tested with; semver inside the fixed group covers that, including the `@internal` exports siblings import from each other ("Semver from 1.0"), and the floor is always the tested version because `changeset version` raises it on every release (`updateInternalDependencies: "patch"`). `"*"` / always-latest was rejected: it crosses majors silently, and `changeset version` does not rewrite it. Peer dependencies for `contract` / `protocol` were rejected: consumers would install core packages by hand, and Changesets bumps peer dependents awkwardly. `check:deps` asserts the `^<current version>` form for every internal dependency (prod and dev). Consumers keep every `@ts-pf/*` package on one major; within it, `npm update`, or Renovate / Dependabot grouped or not, is enough.

### Semver from 1.0

From `1.0.0`, every published package follows semver, judged by what a consumer's code and peers see. **Major:** removing or renaming an export, entry point, or `bin`; narrowing what a caller may pass (a new required option, a narrower parameter or schema-derived input type); changing an inferred output or error type so that correct code stops compiling; changing documented runtime behavior; a wire change an older peer rejects (also a protocol major, `PROTOCOL.md`); raising `engines.node` or a peer-dependency floor, or dropping a peer major. **Minor:** a new export, option, entry point, or peer major (after testing); widening what a caller may pass. **Patch:** a fix that makes the types or runtime match documented behavior, even when code that relied on the wrong type stops compiling (the 0.6.1 union-input fix is the model; say so in the changeset), and doc / skill changes. Exports tagged `@internal` are shared between ts-pf packages (`@ts-pf/message` backpressure helpers, `frameByteLength`, `@ts-pf/server` `isImplementedProcedure`): they make no promise to consumers, but they are still a contract between siblings. Caret ranges let an older sibling run against a newer one (`mcp@1.0.0` with `server@1.3.0`), so within a major an internal export may only gain (a new export, a new optional parameter); changing or removing one is a major. Third-party peer ranges are capped at the majors they were tested with (`astro >=7.0.0 <8`); widening one is a minor. The 1.0 release itself spent the free breaks: the renames `JsonCodec`, `FetchInterceptor`, `McpEffect`, and `MapperOptions`, the removal of `@ts-pf/message`'s deprecated `localFailure` re-export, and the unexporting of helpers no consumer used. Package majors and the wire are separate: `PROTOCOL_MAJOR` and the `PROTOCOL.md` revision move only with the wire, and "protocol 2" in this file means the wire; "package 2.0" means the next package major.

### Trusted publishing, no `NPM_TOKEN`

Releases authenticate with GitHub OIDC through npm trusted publishers, so no long-lived publish token exists to leak. The non-obvious consequences are recorded in `.changeset/README.md` and `CONTRIBUTING.md` ("Releasing"): `registry-url` on `actions/setup-node` writes an empty `_authToken` and makes npm skip OIDC, and the release job pins the Node and npm versions the flow was verified with.

### Consumer skills ship inside each package

`packages/<pkg>/skills/ts-pf-<pkg>/SKILL.md` versions with the package it documents, so an agent that syncs skills from `node_modules` gets the docs for the version it has installed. A separate `@ts-pf/skills` package would drift from the code by at least one release, and a library `postinstall` that syncs skills into a consumer's repo is a supply-chain smell the project refuses. The hub skill on `contract` names opt-in packages the consumer has not installed, because that is the one package every consumer has.

### Docs site is `site/`, not `packages/docs`

`@ts-pf/docs` is the procedure-catalog library (`catalog()`, `docs()`). Putting the Starlight site in `packages/docs` would collide with that name and pull a private Astro app into the library DAG (`check-deps` requires every `@ts-pf/*` directory under `packages/` to be in `PROD`). `site/` is a workspace outside `packages/`, private, Changesets-ignored. Package pages are generated from READMEs at build time (the hexok pattern) so a public API change that updates the README is the docs-site change; generated copies are gitignored and must not be edited.

### README and SKILL are different surfaces (`Q8`)

The README is the npm page: narrative, install line, one snippet, and (since the review) an `API` list. The skill is the agent cheat-sheet: `Do` / `API` / `Pair with` / `Don't`. They were drifting (identifiers in one and not the other, review `O8`), so `check:skills` asserts that every symbol a skill lists under `API` is named in the package README. The direction is skill → README because the skill's `API` section is the explicit export list and the README is where a human lands first.
